# Myoko internal audio upstream status

Research date: 2026-09-20. Exact-model reference: [`jc372/A16UbuntuBuild` at `3de6f0a`](https://github.com/jc372/A16UbuntuBuild/tree/3de6f0a4921641dde5fae0e912725821b7396c55). Kernel reference: linux-next [`1a1de54f`](https://git.kernel.org/pub/scm/linux/kernel/git/next/linux-next.git/commit/?id=1a1de54f7369cd2b5bac0f265910e60ad3a6b4c3), the commit reported by that repository.

## Conclusion

The UX3607OA is **not missing upstream board or machine-driver support**. Mainline has a DT sound card for its internal speakers and microphones using the reused X1E80100 ASoC machine driver, AudioReach/Q6APM, two WSA SoundWire buses, four WSA8845 amplifiers, and a two-DMIC VA capture path. The upstream board submission explicitly reports four-speaker playback working, and later first-party topology and DT work reports the two internal microphones working with format caveats. The 3.5 mm combo jack is physically present but is not wired into the current board DTS/topology/UCM path.

The conflict in this repository is an attribution and reproducibility issue:

- The claim in [`ux3607oa-linux-reference.md`](ux3607oa-linux-reference.md) that the pinned **A16UbuntuBuild** reference reports playback working is incorrect. Its first fetchable public revision and current root commit both say internal speakers are not working ([original audio page at `73af3b8`](https://github.com/jc372/A16UbuntuBuild/blob/73af3b8d6a7a21959dc7cfba9d39da55ea719998/docs/audio.md), [current README](https://github.com/jc372/A16UbuntuBuild/blob/3de6f0a4921641dde5fae0e912725821b7396c55/README.md#end-state)).
- The working-playback report comes instead from the upstream UX3607OA DTS submission and merged commit, whose author lists **"Audio playback (4 speakers)"** as working ([patch discussion](https://ratatoskr.run/linux-arm-msm/2026/07/17291991/t), [merged commit `e8fbbca9`](https://github.com/torvalds/linux/commit/e8fbbca94db752ab94d9dadf2f65872905eafecd)).
- The exact-model A16UbuntuBuild author's more detailed measurement is also real: after loading the ADSP and borrowing the CRD topology, ALSA reached `RUNNING`, but `hw_ptr` stayed zero, only an amplifier power-up crack was audible, and the second SoundWire bus logged clash/overflow/parity errors ([dated audio state](https://github.com/jc372/A16UbuntuBuild/blob/3de6f0a4921641dde5fae0e912725821b7396c55/notes/2026-09-16-hermes-audio-state.md)). Therefore upstream playback support exists, but that repository did not reproduce it on its unit/build.

## Kernel and board description

The board DTS already contains the integration that the older A16UbuntuBuild `docs/audio.md` says is absent. Its `sound` node uses `qcom,glymur-sndcard`, names the card `GLYMUR-ASUS-Zenbook-A16-UX3607OA`, and defines `WSA Playback` plus `VA Capture`. Playback connects `WSA_CODEC_DMA_RX_0` to left/right woofer and tweeter WSA8845s across `swr0` and `swr3`; capture connects `VA_CODEC_DMA_TX_0` to `VA DMIC0/1` ([pinned board DTS](https://git.kernel.org/pub/scm/linux/kernel/git/next/linux-next.git/tree/arch/arm64/boot/dts/qcom/glymur-asus-zenbook-a16-ux3607oa.dts?id=1a1de54f7369cd2b5bac0f265910e60ad3a6b4c3), [merged source](https://raw.githubusercontent.com/torvalds/linux/e8fbbca94db752ab94d9dadf2f65872905eafecd/arch/arm64/boot/dts/qcom/glymur-asus-zenbook-a16-ux3607oa.dts)).

The shared Glymur DTSI supplies the ADSP remoteproc, GPR services, Q6APM/Q6PRM, LPASS WSA/VA macros, SoundWire masters, and LPI pinctrl ([Glymur DTSI](https://github.com/torvalds/linux/blob/6a5719cc3ef2e4d9857cc4ae18e6db09d59a8cc9/arch/arm64/boot/dts/qcom/glymur.dtsi)). The existing X1E80100 machine driver gained `qcom,glymur-sndcard` support in commit [`8c7ea986`](https://github.com/torvalds/linux/commit/8c7ea98650e644ff61d3774085f732b40d8f7788); it handles SoundWire stream setup and four-channel mapping. It also caps combined speaker gain at -3 dB because active speaker protection is not implemented ([driver source](https://github.com/torvalds/linux/blob/6a5719cc3ef2e4d9857cc4ae18e6db09d59a8cc9/sound/soc/qcom/x1e80100.c#L34-L51), [gain-limit commit](https://github.com/torvalds/linux/commit/0a5ee0e520eff98ee2b4568194562870877b050f)). Myoko's evaluated kernel config already builds `qcom_q6v5_pas`, `snd_soc_x1e80100`, QDSP6, the WSA/VA macros, `soundwire_qcom`, and `snd_soc_wsa884x` as modules, matching upstream arm64 defconfig ([pinned defconfig](https://git.kernel.org/pub/scm/linux/kernel/git/next/linux-next.git/tree/arch/arm64/configs/defconfig?id=1a1de54f7369cd2b5bac0f265910e60ad3a6b4c3)).

## Firmware and topology

The board asks for these OEM remoteproc files under `/lib/firmware/qcom/glymur/ASUSTeK/UX3607OA/`:

- ADSP/audio: `qcadsp8480.mbn`, `adsp_dtbs.elf`.
- CDSP: `qccdsp8480.mbn`, `cdsp_dtbs.elf`.
- SoCCP names also appear in the DTS, but this machine normally attaches to the firmware-started SoCCP; A16UbuntuBuild notes that ASUS's package contains no `soccp.mbn` pair and says not to rename `RSCP.bin` ([firmware extraction instructions](https://github.com/jc372/A16UbuntuBuild/blob/3de6f0a4921641dde5fae0e912725821b7396c55/steps/00-prepare-in-advance.md#04-firmware-from-this-machines-windows-install)).

Audio additionally needs the topology requested by the kernel as:

```text
qcom/glymur/GLYMUR-ASUS-Zenbook-A16-UX3607OA-tplg.bin
```

That name is derived directly from the machine driver's `glymur` driver name and the DTS card model ([topology loader](https://github.com/torvalds/linux/blob/6a5719cc3ef2e4d9857cc4ae18e6db09d59a8cc9/sound/soc/qcom/qdsp6/topology.c#L1415-L1439)). The exact A16 topology source was merged on 2026-09-01 and describes four speakers plus two DMICs ([topology PR 75](https://github.com/linux-msm/audioreach-topology/pull/75), [source](https://github.com/linux-msm/audioreach-topology/blob/993a17dcb672357998a463a73f120064d6c74f4f/GLYMUR-ASUS-Zenbook-A16-UX3607OA.m4)). The source changes the capture device arguments to `S32_LE` and one or two channels. However, the current shared device-subgraph macros do not serialize those arguments. Compiling the unmodified A16 and CRD sources at commit `993a17d` produces the same 11,320-byte binary with SHA-256 `ea851335b7e8e13977a597250f2c0f1b6434d68f2248ae85a332e158fd64db57`. The A16 source also leaves the capture frontend capability at `S16_LE`, while the proposed UCM profile requests `S32_LE`; that combination cannot work with the pinned kernel because its Q6APM capture PCM advertises only `S16_LE` and `S24_LE`. The hardware author reports `S24_LE` working, so Mountainous changes the A16 capture frontend to `S24_LE`, producing SHA-256 `9442de20fd79cbe3543ac5be882197ec4db830344ce70f57ef98ceabdc4ddf11`. The UCM policy exposes capture at `S24_LE` now that the framing fix is verified. A live test that added Q6APM `S32_LE` support failed when the DSP rejected VA port 110 at stream start. Thus the missing model-named topology explains why the card cannot bind by its proper name, but the unmodified binary contents do **not** explain A16UbuntuBuild's frozen CRD playback path.

At linux-firmware tip [`2b8daaf6` (2026-09-19)](https://gitlab.com/kernel-firmware/linux-firmware/-/blob/2b8daaf611fbade74f26a5b58ec1defe6a02f5e0/WHENCE#L9973-9976), `qcom/glymur` still has only the generic ADSP/CDSP files and `GLYMUR-CRD-tplg.bin`; the compiled A16 topology has not yet been synchronized. It must presently be built from the first-party topology source and installed at the kernel-requested path (or through the usual top-level symlink to its OEM subdirectory). The matching ALSA UCM proposal is also still open and currently adds only speaker and internal-microphone policy ([UCM PR 845](https://github.com/alsa-project/alsa-ucm-conf/pull/845)).

## Initrd timing on Myoko

ADSP startup races switch-root. One captured boot requested `qcadsp8480.mbn` at 5.568 s after switch-root, while the final verified boot requested it at 4.596 s and completed ADSP startup at 4.991 s. A failed remoteproc start does not retry automatically. Mountainous therefore keeps the signed ADSP image and matching device trees in both the real-root firmware closure and the initrd; the topology is needed later at card probe. Installing the files after a failed probe requires manually starting the offline remoteproc or rebooting because the codec and machine drivers probe in dependency order ([A16 firmware installer](https://github.com/jc372/A16UbuntuBuild/blob/3de6f0a4921641dde5fae0e912725821b7396c55/scripts/a16-install-firmware.sh#L71-L102)).

Before this change, Mountainous omitted all of these audio files from its deliberately trimmed firmware closure ([`modules/glymur.nix`](../../modules/glymur.nix#L145-L162)), matching Myoko's observed `-ENOENT` ADSP failure and Dummy Output state.

## What is actually reported working

| Endpoint | Best supported conclusion |
|---|---|
| Internal speakers | **Verified working on Myoko.** Four-channel UCM playback produced a clean 440 Hz tone, a smooth 220–2200 Hz sweep, and clean normal program audio. All four WSA8845 amplifiers remained attached without new SoundWire or DSP faults. |
| Internal microphones | **The signal was always real; the driver framed it wrong.** Direct ALSA capture opened as `S24_LE` looks like full-scale uncorrelated noise, and no gain, clock, decimator, DMIC pair, or mute-key change alters it. Reading the same bytes as packed 3-byte stereo (`scripts/analyze-myoko-mic-framing.py`) recovers a clean signal: lag-1 autocorrelation 0.99, left/right correlation 0.999, RMS about 0.002 at room noise. The cause is in `q6apm-dai.c` and `audioreach.c`: for `S24_LE` the driver sends `bit_width = 24` and also `bits_per_sample = 24`, so the DSP writes packed 24-bit frames into a buffer ALSA reads as 4-byte words. Playback never hit this because PipeWire opens the speaker PCM at `S16_LE`. `modules/glymur/0005-…-keep-S24-LE-in-32-bit-containers.patch` sends `bits_per_sample = 32` for `S24_LE`. The earlier `S32_LE` experiment failed for a different reason (VA port 110 rejected the backend format) and stays out. **Verified on 2026-09-20 with the patched kernel deployed:** `scripts/test-myoko-audio-microphones` passes with the recorded framing coherent (lag-1 0.99, L/R 0.9994), and the user confirmed an 8-second spoken sentence played back clearly. Raw level is low (speech about −52 dBFS RMS at `VA_DEC Volume` 84), so gain is a PipeWire/UCM concern, not a kernel one. The UCM profile now exposes `SectionDevice."Mic"` on `hw:0,1` with `Format S24_LE`; `scripts/test-myoko-audio-ucm` requires that format and rejects `S32_LE`. With generation `gn7vp3vq…` deployed, PipeWire exposes `alsa_input.platform-sound.HiFi__Mic__source` ("Built-in Audio Internal microphones"), opens `hw:0,1` at `S24_LE`/48 kHz/stereo, and the user confirmed a second spoken sentence recorded with `pw-record` played back clearly. |
| 3.5 mm headphone/headset jack | **Not currently supported by this DT audio path and no working Linux report found.** ASUS specifies a combo jack, and the UCM proposal's comment recognizes one WCD headset, but that proposal intentionally adds only speakers and DMICs. The board DTS has no WCD/RX/TX SoundWire codec or headset DAI link ([ASUS specification](https://www.asus.com/us/laptops/for-home/zenbook/asus-zenbook-a16-ux3607/techspec/), [UCM diff](https://github.com/alsa-project/alsa-ucm-conf/pull/845.diff)). This also leaves the headset microphone unsupported. |
