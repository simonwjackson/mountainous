# Myoko window session restore

Myoko uses [hypr-session-restore](https://github.com/UpayanChatterjee/hypr-session-restore), pinned as a non-flake input. Its user service starts with `hyprland-session.target`, restores the last snapshot at graphical login, and saves every 60 seconds after a 90-second startup delay. The service also saves when it stops. Other hosts do not run it.

`modules/myoko-session-restore.nix` adapts the pinned script through `modules/myoko-session-restore-patch.py`. The patcher rewrites the CLI calls for Myoko's Hyprland Lua instance, adds Ghostty's working-directory option, sets the snapshot directory to mode 0700 and the file to mode 0600, and does not overwrite a good snapshot with an empty one. This last change protects against shutdown racing with the save daemon. It splits Chromium's one-field process command into executable and flags. For Chromium app windows whose class matches the `--app=` URL, it saves `/run/current-system/sw/bin/web-app <url>` instead of replaying Chromium's internal process command. This is Myoko's existing launcher in `modules/web-apps.nix`; it gives Forgerie the correct app window class. Regular Chromium windows also need `/run/current-system/sw/bin/chromium`, not Chromium's unwrapped process binary. The wrapper sets its sandbox and library environment. The saver counts launch attempts by process ID and window class, not process ID alone, because Chromium app and browser windows can share a process. To suppress the next restore, create `~/.local/state/hypr-session-restore/disabled`. Delete the snapshot to forget the saved windows.

The patcher also replaces upstream's best-effort sweep with deterministic placement. Upstream launched every saved window and moved only the clients it happened to see, matching by class and preferring the saved numeric workspace. That failed on Myoko for three reasons. Single-instance apps (Zed, Chromium) ignore the per-launch workspace rule, so their extra windows arrive on the wrong workspace. Upstream's 20-second sweep ended before slow apps appeared. And the Lua strip renumbers occupied workspaces to 1..N, so a saved numeric id is not stable across a restart. The replacement saves each normal workspace as its strip position, waits up to 45 seconds for the saved windows to appear, matches saved windows to live clients by class and title first and then by class, and moves each matched client to its saved position in ascending order. It retries placement until the workspaces hold, and reports any saved window that never reappeared. The service sets `TimeoutStartSec = 300` so the longer restore cannot be killed mid-flight.

This feature relaunches processes and puts their windows on saved workspaces. It does not restore unsaved edits, terminal scrollback, Chromium tabs, or Zed buffers; each application controls its own document and tab recovery. Zed reopens its extra window by itself, so placement can move it. Chromium did not reopen its second browser window in the generation-12 trial, so that window stays missing until Chromium's own session restore is enabled; placement cannot invent it. Tiled layout depends on Myoko's capacity and compaction rules. The strip renumbers occupied workspaces to 1..N, so the restore saves positions, not raw ids, and places each window on its position. Multiple windows on one workspace assume that workspace's capacity, which the compositor does not persist across a restart. The snapshot includes process launch commands, which can contain sensitive arguments; do not publish the JSON file.

Before the first reboot, `scripts/test-myoko-session-restore-target` saved five real Myoko windows and checked the private snapshot permissions. Calling `restore` while those five windows were still open did not duplicate them. The Hyprland Lua launch dispatcher also accepted the script's `hl.dsp.exec_cmd` form. On the first generation-8 boot, Tailscale joined successfully, but only four of five saved windows returned: the Forgerie PWA failed to launch because its single-field command line was quoted as one executable. The five-window snapshot was preserved at `~/.local/state/hypr-session-restore/session.pre-gen8-20260925.json` before autosave could replace it. `scripts/test-myoko-session-restore-command` reproduces the bad launcher with the old script and passes with the tokenization fix. On the generation-9 one-time boot, Linux 7.2.7 and the original Tailscale identity returned, but the PWA was still missing. A second regular Chromium window was open at inspection, but the user opened it manually; it is not evidence of a restore failure mode. The five-window snapshot from before that boot is kept at `~/.local/state/hypr-session-restore/session.pre-gen9-20260925.json`. Launching the same URL through Myoko's `web-app` binary reopened the PWA with the correct class in the live session. On the generation-10 one-time boot, Linux 7.2.7 and the original Tailscale identity returned. The Forgerie PWA was present with its correct class at the first GUI check, without an agent launching it. The user manually opened regular Chromium after it failed to return, so only four of five windows restored automatically. The browser's saved command pointed at the unwrapped Chromium binary. A headless trial on Myoko using the saved binary exited with signal 4; the installed Chromium wrapper exited with status 0 and produced a page. The PWA and manually opened Chromium workspaces were swapped against the preboot snapshot; exact placement remains unverified. The corrected browser launch after login has not yet been tested. A later live snapshot had two regular Chromium windows and a Forgerie PWA; one browser and the PWA shared a process ID. The old process-only deduplication marked the PWA not to spawn. `scripts/test-myoko-session-restore-command` now checks one launch per class for a shared process ID. On generation 12, a live save recorded six windows: two regular Chromium windows and the PWA. Both browser commands used the installed Chromium wrapper, and the PWA was marked to launch. On the generation-12 one-time boot, Linux 7.2.7, the original Tailscale node, LAN SSH, and tailnet SSH worked. Six windows were saved before reboot. After login, one regular Chromium window was missing and both Zed windows were on workspace 1 instead of workspaces 1 and 2. Forgerie was on workspace 2 instead of 3, and the remaining Chromium window was on workspace 3 instead of 4 or 5. A first check showed two Forgerie windows, but a later check showed one; the final five-window state still failed both class counts and workspace placement. `scripts/test-myoko-session-restore-placement` loads the built script, injects a fake Hyprland, and asserts that every saved window ends on its saved workspace position, including a single-instance app whose second window arrives from the app itself. It also covers workspace-position mapping, class-and-title matching, missing windows, and floating, pinned, and fullscreen windows. `scripts/test-myoko-session-restore-command` checks the launcher rewrites and the shared-process spawn rule. Neither test replaces a real login restore. The private six-window snapshot from before the generation-12 trial is `~/.local/state/hypr-session-restore/session.pre-gen12-20260925.json`. Generation 6 remains the EFI default. Do not use the saved snapshot as a substitute for saving work in applications.
